# ③·④ 프롬프트 틀

공통 머리 (모든 agent 앞에 붙인다):

```
- 보고서 A: <경로>
- 보고서 B: <경로>
- 주제: <한 문장>
- 원본: <저장소·브랜치(git show "${B}:path")·서버 저장소·공식 문서 출발점>
- 출력: <scratchpad>/<주제>-review/<역할>.md 에 쓰고, 답장에는 <요점 형식>만. 한국어
- 코드·문서 수정 금지, 외부 게시 금지. 내려받은 바이너리는 빈 새 디렉터리에 두고 실행하지 않는다
```

## 대조

```
판정·권고는 하지 말고 대조만 한다.
1. 두 보고서를 끝까지 읽는다.
2. 주장 단위 표: | 주제 | A 주장 | B 주장 | 상태 (일치 / 불일치 / A만 / B만) | 각 근거 |
   주제 묶음: <조사 항목 목록>
3. 불일치는 어느 쪽 근거가 더 직접적인지(원문 인용·코드 줄 vs 추정) 한 줄.
4. 두 보고서 모두 추정이거나 근거 없는 주장 목록.
답장: 불일치만 bullet 10개 이내.
```

## 근거 검증

```
보고서 작성자를 믿지 않는다.
1. 결론을 좌우하는 사실 주장 15~25개를 고른다 (코드 file:line, 공식 문서 인용, 시그니처, 의존성, 버전, 수치).
2. 각 주장을 원본에서 확인한다: 코드는 해당 줄을 직접, 웹 문서는 원문 문장, 패키지는 POM·공개 시그니처(javap -public 만), GitHub 는 gh api.
3. 표: | 주장 | 보고서 | 판정 (맞음 / 틀림 / 반만 맞음 / 미확인) | 확인한 원본 |
답장: 틀림·반만·미확인만.
```

## 반대 입장

```
두 보고서의 공통 결론이 틀렸다고 가정하고 가장 강한 반론을 세운다.
- 공통 결론 요약: <main 이 2~3줄>
- 반론 방향 (각각 최소 1개, 근거 포함): <결론의 반대 선택지들>, 보고서가 놓친 더 나은 대안
각 반론: 주장 / 근거 / 성립하면 바뀌는 결론 / 반론의 약점.
마지막에: 결론이 흔들리는 조건(미확인 사실)을 정리.
답장: 가장 강한 반론 3개.
```

## 구현 현실성

```
권고·로드맵을 실제 코드와 제약에 대어 보고 그대로는 안 되는 곳을 찾는다.
- 코드 규칙·빌드 설정·배포 경로: <경로>
- 알려진 결정: <사용자 결정>
1. 제안마다: 바꿀 곳(file:line), 플랫폼별 가능 여부, 빌드·난독화·배포 영향.
2. 보고서 사실 중 코드와 어긋나는 것.
3. 순서 의존 (무엇이 먼저 머지·배포돼야 하나).
표: | 제안 | 출처 | 바꿀 곳 | <플랫폼별 칸> | 막히는 점 |
답장: 그대로는 안 되는 제안만.
```

## 누락

```
보고서가 사용자 질문에 답했는지 확인한다.
- 사용자 질문 원본: <지시서 경로들, 사용자가 처음 물은 문장>
1. 질문마다: | 질문 | A 답 위치·충분성 | B 답 위치·충분성 | 빠진 것 | (답함 / 일부 / 안 함)
2. 범위 밖으로 새거나 길어진 부분.
3. 세션 scratchpad 경로에만 있는 근거 인용 목록 (경로 그대로).
4. 두 보고서 모두 다루지 않은, 사용자 결정에 필요한 질문.
답장: 빠진 것과 4번.
```
