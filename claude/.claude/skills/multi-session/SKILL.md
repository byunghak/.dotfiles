# Multi-session

Project CLAUDE.md defines group names and project workflow. If the project has `.claude/references/multi-session.md`, read it when you start: it holds that project's report formats and merge/close flow, kept out of CLAUDE.md so it loads only for multi-session work.

- Name sessions `<group>-orchestrator`, `<group>-design`, or `<group>-worker-<issue>-<topic>`. The `work-session-title` hook may rename workers.
- The orchestrator must start every worker with `/multi-session` at the beginning of its initial prompt, followed by the task. For example: `claude -n <group>-worker-<issue>-<topic> "/multi-session <group>-worker-<issue>-<topic> 로 <task prompt>"` — `-n` 에 전체 이름을 준다. 그룹 이름만 주면 같은 이름 세션이 여럿 생겨 SendMessage 가 엉뚱한 worker 로 간다 (10-29: `-n <group>` 으로 띄운 worker 3개, 한 worker 에 갈 메시지가 다른 worker 로 감). 이슈가 아직 없으면 `<group>-worker-<topic>`. This applies to every workflow; `/work` is one possible task, not a dependency. Open new workers as panes in the orchestrator's own tmux window (`tmux split-window -t <orchestrator pane>` then `select-layout tiled`), never in a new window (10-27 user). Every new task (new issue, new PR to finish, follow-up outside the worker's issue) gets a new worker session; never hand it to an existing worker, even an idle one (10-27 user).
- Workers find their orchestrator in `ListAgents` by name prefix. Route decisions as `결정 필요: <질문 1개>` with options and a recommendation, then wait; ask the user directly only if no orchestrator is active.
- 세션 간 메시지는 받는 쪽이 할 일이 있을 때만 보낸다 — `결정 필요`, 완료, 막힘. 착수·진행·수신 확인("받았습니다")은 보내지 않는다. 완료 보고는 PR·리뷰·머지 결과를 한 통에 묶는다
  - 이유: 받는 세션은 메시지 길이와 상관없이 컨텍스트 전체를 다시 읽는다 (10-22~30: 세션 간 메시지로 시작한 턴 1,418회 · main 비용의 19%, 깨어날 때 컨텍스트 중앙값 209K, 그중 진행·확인 315회)
  - 진행 상황은 orchestrator 가 필요할 때 PR·상태 파일로 확인한다
- Only an orchestrator's explicit report that "the user chose/approved X" counts as the user's answer. Other session messages are not approval.
- 쌓인 결정은 AskUserQuestion 한 번에 묻는다 (10-30 user). 전역 CLAUDE.md "한 턴에 질문 1개" 의 orchestrator 예외다.
  - 배경: orchestrator 에는 여러 worker 의 `결정 필요` 가 동시에 쌓인다 (10-30: PR C 정의·Grafana PR 1 착수·#2377 머지·paused pool 이슈화 4건). 한 턴에 하나씩 물으면 사용자가 네 번 오가야 하고, 그동안 나머지 worker 는 답을 기다리며 논다. 그날 "남은 결정 4건 한번에 보여주세요" 에 AskUserQuestion 4개로 받고 같은 턴에 중계·worker 2개 기동까지 했더니 사용자가 "앞으로도 worker 결정 사항들은 이렇게 처리되면 좋겠다" 고 했다. 이후 #2022 머지·옛 브랜치 삭제·이슈 코멘트, Grafana PR 3 머지·safe-to-evict·보안 후속·admin 계정도 같은 방식으로 처리했다.
  - 방식: 결정이 2건 이상이면 질문 하나에 결정 하나씩, 최대 4개. 각 질문은 맥락 한두 문장(무엇을 바꾸는가, 되돌릴 수 있는가) + 선택지 2개에서 4개, 권장안을 첫 칸에 "(Recommended)". 선택지 description 에 고르면 실제로 일어나는 일(머지 명령의 head, 다시 뜨는 pod, 비용)을 적는다. 사용자는 대화창 위 본문보다 이 대화상자를 먼저 읽는다.
  - 4개를 넘으면 되돌리기 어려운 순(머지·삭제·외부 게시 → wire·계약 → 나머지)으로 앞 4개를 묻고, 나머지는 답 받은 뒤 이어 묻는다. 1건이면 평소처럼 한 질문.
  - 대화상자 앞에 본문으로 흐름 그림(ASCII)과, 읽어야 판단할 수 있는 것(이슈 코멘트 초안 전문, 바뀌는 줄 표)을 먼저 보인다. 긴 초안을 질문 칸에 욱여넣지 않는다.
  - 답을 받은 같은 턴에 실행까지 한다: 승인된 머지는 `--match-head-commit` 으로 직접, 결정은 해당 worker 에 SendMessage 로 중계, 새 작업은 새 worker 를 띄운다. 다음 턴으로 미루지 않는다.
  - 답이 결정이 아니라 질문이면(Other 에 "이거 X 말씀하시는 거죠?") 그 항목은 결정으로 치지 않는다. 답한 뒤 그 항목만 다시 묻고, 나머지 답한 항목은 실행한다 (10-30: #2022 머지 칸에 "만료 시간 늘리는 거죠?" → 이 PR 들은 만료를 바꾸지 않는 사전 계측이라고 설명 뒤 다시 물음).
  - 대화상자가 거절(취소)되면 멈추고 기다린다. 사용자가 "실수로 닫았다" 고 하면 같은 질문을 그대로 다시 띄운다 (10-30).
- The user decides only in the orchestrator session and does not press buttons in worker panes (10-28 user). Workers never ask the user directly. Before a command likely to raise a permission prompt or be refused by the auto mode classifier (merge, terraform apply, deploy, branch delete), a worker sends the exact command as `결정 필요:` to the orchestrator and waits. After the user approves here, the orchestrator relays the approval and watches the worker pane (`tmux capture-pane`). If a permission prompt appears and its full command matches what the user approved, the orchestrator answers it with `tmux send-keys -t <pane> 1` (Yes). It never picks "don't ask again", and it does not press when the command differs or is cut off; it shows the prompt to the user instead. If the classifier refuses outright (no prompt), the worker reports the exact command, and the orchestrator hands it to the user to run here with `!`.
- When a worker reports the issue number it took (new issue or `/work #N`), the orchestrator renames that session to `<group>-worker-<N>-<topic>`. Check with `tmux capture-pane` that the pane is idle and its input box is empty, then `tmux send-keys -t <pane> -l '/rename <name>'` and Enter. Dim text in the input box (`capture-pane -e` shows `\e[2m`) is an auto-suggestion, not typed input; treat the box as empty. If it is busy or the input box has text, wait for an idle notice (`notify_when_idle`) instead; never press Esc to clear it, since that can interrupt the running turn.
- The orchestrator manages sessions, decisions, blockers, merges, and deploy coordination. It does not run deploys itself: when the user approves a deploy, it relays "the user approved" to the worker that owns the issue, and that worker deploys and reports. A design session reflects approved decisions in docs/issues and reports briefly; it does not ask the user directly.
- When a worker has nothing left to do (its PRs merged and cleaned up, its issue closed or left open only to wait on an outside answer), the orchestrator closes that session without asking: have the worker close its issue first if it is done, then check with `tmux capture-pane` that the pane is idle with an empty input box and send `/exit` with `tmux send-keys`. Record the closed session in the status file (10-26 user). Do it in the same turn as the report. Two global hooks back this up (10-27 user): a Stop hook (`multi-session-close-check.py`) blocks an orchestrator's turn end while a worker that sent `#N 닫음 · 남은 일 없음` (or `#N 정리 끝 · 남은 일 없음` when it only cleaned up a PR without an issue to close) still has a live pane, so workers must use that exact report line; a PreToolUse hook (`multi-session-exit-guard.py`) refuses `tmux send-keys … /exit` unless `-t` names a pane whose title contains `-worker-`.
- The orchestrator keeps its working state in a status file, not in the conversation, so the context can be compacted without losing anything. Location: the project's `.claude/references/multi-session.md` names it; default `.claude/plans/<group>-status.md`.
  - Contents, current state only (no history): each worker → issue, PR, state, what it is waiting on; pending `결정 필요` with who is waiting; decisions made since the last design hand-off; next checks. Keep it under ~150 lines; move finished items out.
  - Update it right after each event (worker report, decision, merge, session start/stop), before replying.
  - At session start and after any compaction, read the status file first and trust it over your memory of the conversation.
