# understand 출력 형식

목적: 엔지니어가 PRD 를 처음 읽을 때 걸리는 지점을 미리 풀어준다. 요약이 아니라 **설계에 들어가기 위한 지도**다.

## 00-understand.md

```markdown
# <PRD 제목> — 이해 노트

PRD 최종 수정: <시각> · 작성: <날짜>

## 한 문단 요약

<무엇을 왜. 3~5문장>

## 핵심 흐름

<ASCII 또는 mermaid. 단계마다 PRD 절 번호>

## 용어

| 용어 | 한 줄 정의 | 이 PRD 에서의 의미 |

- PRD 용어집 + PRD 가 정의 없이 쓴 용어

## 컴포넌트

| 컴포넌트 | 신규 / 확장 / 기존 활용 | PRD 절 | 걸친 repo |

## 엔지니어 위임

| PRD 절 | 항목 | PRD 가 정한 것 | 엔지니어가 정할 것 |

## 미결정

| PRD 절 · 번호 | 항목 | 출처 (PRD open decision 은 PRD 번호 그대로 / 본문 암묵적은 번호 없음) | 막히는 위임 항목 (PRD 절로) |
```

## 쓰는 규칙

- 결론 먼저, 쉬운 말. 수식·코드 경로를 먼저 던지지 않는다
- 추상 비유어(축·노브·경계·층) 대신 구체어
- 낯선 용어는 처음 쓸 때 한 줄 정의
- PRD 의 표현을 그대로 옮기지 말고, 엔지니어가 "그래서 무엇을 만들어야 하나" 를 알 수 있게 다시 쓴다
- 위임 범위: PRD 가 이미 정한 제약(예: first-price, 정산 KPI)과 엔지니어 재량을 구분한다
- 암묵적 미결정 신호: "~가 필요하다", "결정 사항이다", "확인되지 않았다", "선행 검증"

## 터미널 요약

- 한 문단 요약 + 핵심 흐름 ASCII + 위임 N개 / 미결정 N개 개수
- 나머지는 파일 경로로 안내
