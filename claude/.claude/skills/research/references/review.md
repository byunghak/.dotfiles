# 설계를 좌우하는 조사: 독립 조사 2 + 비판

조사 한 번은 그 조사자의 착오를 그대로 싣는다. 독립 조사 둘을 대조하고, 다른 관점의 비판으로 걸러낸 뒤에야 결론으로 쓴다.

```
① main: 1차 조사 → 지시서 ──▶ ② 조사 ×2 (독립) ──▶ ③ 대조 ┐
                                              ├▶ ④ 비판 ×4 (병렬) ──▶ ⑤ main 종합
                                              ┘
```

배경: 11-08 MAX adapter 호환성 조사. `deep-research` 두 번(A·B) 모두 "모양만 MAX, 자체 계약" 으로 같은 결론을 냈다. 그러나 결론을 바꾸는 사실 셋(Kotlin default 메서드의 바이너리 비호환, load 타임아웃 없음, `Class.forName` 초기화 순서)과 보고서 오류 셋은 비판 단계에서만 나왔다. `deep-research` 에는 비판·검증 단계가 없다 (분해 → 병렬 조사 → 보고서 작성).

## ① 1차 조사와 지시서 (main)

- 몇 번의 검색·코드 읽기로 출발점을 잡는다: 공식 문서 위치, 원본(아티팩트·헤더·코드) 위치, 이미 확인된 사실
- 지시서에 넣는 것: 배경·사용자 결정, 이미 확인한 것 (다시 찾지 않게), 조사 항목, 산출 경로, 금지 사항
- 사용자가 프롬프트를 직접 주면 그대로 쓰고, 맨 위에 "실행 조건"(저장소·브랜치·산출 경로·금지 사항)만 덧붙인다

## ② 독립 조사 2개

- 각자 `anthropic-skills:deep-research` 로 진행한다. 조사 subagent 는 model sonnet
- 두 조사는 서로의 산출물을 읽지 않는다. 지시서에 명시하고, 산출 경로를 다르게 준다 (`…-research.md`, `…-research-b.md`)
- 실행 형태
  - 기본: Agent subagent 2개를 한 메시지에서 병렬로 (main 에는 결론만 돌아온다)
  - 30분 이상 걸릴 조사나 사용자가 진행을 보고 싶을 때: multi-session worker 세션 (`orchestrator` skill 로 띄움)
- 두 지시서를 일부러 다르게 써도 된다 (하나는 main 이 구체화, 하나는 사용자 원문). 겹치는 항목이 대조 기준이 된다

## ③ 대조 + ④ 비판 (한 메시지에서 5개 병렬, 모두 sonnet)

프롬프트 틀: `references/review-prompts.md`. 각자 결과를 파일로 쓰고, 답장에는 요점만.

| agent       | 묻는 것                                                                         |
| ----------- | ------------------------------------------------------------------------------- |
| 대조        | 주장 단위 일치 / 불일치 / 한쪽만. 불일치는 어느 근거가 더 직접적인가            |
| 근거 검증   | 결론을 좌우하는 주장 15~25개를 원본에서 다시 확인 (맞음 / 틀림 / 반만 / 미확인) |
| 반대 입장   | 공통 결론이 틀렸다고 가정한 가장 강한 반론, 보고서가 묻지 않은 전제             |
| 구현 현실성 | 권고를 실제 코드·빌드 설정·배포 경로에 대어 보면 안 되는 곳 (file:line)         |
| 누락        | 사용자 질문마다 답했나, 범위 밖으로 샌 것, 사용자 결정에 필요한데 빠진 질문     |

- 대조가 비판의 입력일 필요는 없다. 비판은 두 보고서를 직접 읽는다 — 기다리지 않고 병렬로
- 비판 agent 는 보고서 작성자를 믿지 말라고 지시한다

## ⑤ main 종합

- 결론을 바꾸는 새 주장은 main 이 직접 원본에서 한 번 더 본다 (코드 줄, 공식 문서 문장). agent 보고를 그대로 옮기지 않는다
- 표: | 발견 | 출처 agent | main 확인 여부 |
- 나눠 쓴다: 확인된 사실 / 추정 / 권고 / 흔들린 전제
- 결정이 필요한 것은 보고와 분리해 AskUserQuestion 으로. 보고 안에서는 "남은 결정 N건" 만

## 근거 보존

- 조사자의 javap 출력·헤더·노트는 그 세션 scratchpad 에 있어 세션이 끝나면 사라질 수 있다
- 보고서가 scratchpad 경로를 인용하면, 종합 전에 근거 파일을 보고서 옆 디렉터리(`<보고서>-evidence/`)로 옮길지 사용자에게 묻는다

## 함정

- 웹 문서는 WebFetch 요약이라 "문서에 없다" 는 확정이 아니다 (truncated). 결론에 쓰면 "요약 기준" 으로 표시
- 같은 URL 을 두 조사가 다르게 기록하면 (예: 한쪽 200, 한쪽 404) 근거 검증이 직접 연다
- zsh 에서 `git show $B:path` 는 `:t` 수식어로 깨진다 → `"${B}:path"`
