## Step 1 — 이슈 분석과 진행 상황 파악

이슈에 적힌 요구와 "이미 된 것" 을 먼저 고정한다. 해결책은 아직 생각하지 않는다.

조회 (`<repo>` 는 Step 0 에서 찾은 이슈 리포):

- 이슈: `gh issue view <n> -R <repo> --comments` — 상태·라벨·담당자·본문·댓글·체크리스트
- 연결 이슈: 본문·댓글의 `#<m>` 참조, 상위·하위 이슈 (`gh issue view <m> -R <repo>` 로 제목·상태만)
- PR: `gh pr list --state all --search "<n> in:title,body"` — 머지됨 / 열림 / 닫힘
- 반영 커밋: `git log origin/<BASE> --oneline --grep "#<n>"`, 통합 브랜치 묶음이면 `origin/<통합 브랜치>` 도
- 브랜치: `git branch -a --list "*<n>*"`, `git worktree list | grep <n>`
- 로컬 기록: `.claude/plans/*-<n>-*/` 가 있으면 DESIGN.md·PLAN.md 상태

출력 (터미널, 결론부터):

```
<repo>#<n> <제목> — <open/closed> · <라벨>
요약: <이슈가 요구하는 것 2~3문장>

진행 상황
  완료   <머지된 PR·커밋과 무엇을 했는지>
  진행중 <열린 PR·브랜치·worktree·로컬 plan>
  남음   <이슈 요구·체크리스트 중 아직 근거가 없는 것>

이슈에서 불분명한 점: <있으면>
```

- "남음" 은 이슈 체크리스트·수용 조건과 머지된 PR 을 대조해 판단. 근거 없으면 "확인 못 함" 으로
- 이 요약을 따로 묻지 않고 Step 1.5 작업 그림 → Step 2 Brainstorm → Step 3 PR 분리까지 이어 쓴 뒤 한 답에 보인다 (승인 ①, 묻는 조건은 Step 3)

## Step 1.5 — 작업 그림

Brainstorm 전에 "이 이슈가 무엇을 만드는가" 를 그림으로 보여준다. 대화 중간에 맥락을 잃어도 이 그림으로 돌아올 수 있어야 한다.

- 시스템 그림 (ASCII): 이 이슈가 끼어드는 자리 — 누가 누구를 부르고 무엇이 오가는가
  - 이번 이슈가 만드는 것은 ★, 범위 밖은 `#<번호>` 로 표시
- 값 하나를 끝까지 따라간다: 만드는 곳 → 거치는 곳 → 쓰는 곳 (예: 토큰을 누가 봉인·운반·여는가)
  - 그 값이 왜 그 형태여야 하는가 (암호화·서명·wire 레이아웃 등) 를 한 줄로
- 산출물 표: 만드는 것 | 왜 필요한가 | 쓰는 쪽(후속 이슈)
- 용어 한 줄 풀이: 이슈 본문의 약어·도메인 용어
- 해결책·선택지는 이 그림에 넣지 않는다. 묻지 않고 Step 2 로

## Step 2 — Brainstorm

"남음" 범위만 대상으로 한다.

1. 문제 정의
   - 증상 / 기대 동작 / 재현 조건 / 성공 조건
   - "이슈에 적힌 것" 과 "내 가정" 을 구분해 적는다 (가정은 `## 결정 대기` 에도 한 줄)
2. 현 시스템 파악
   - 문제 지점의 코드 경로·설정 출처를 `file:line` 으로 (`tracing-system-internals` 규칙)
   - 관련 최근 커밋, 개념이 코드에 없으면 GitHub 이슈 검색 (미구현 개념은 이슈에만 있다)
   - 프로덕션 관측이 필요한 문제면 `troubleshoot` skill 로 지표 확인
   - 결과는 ASCII 로 짧게. "현재 동작이 왜 틀렸는가" 가 드러나게
3. 해결 방향
   - 접근법이 갈리면 2~3개 + 권장안 하나
4. 권장 방향으로 `.claude/plans/YYYY-MM-DD-<issue>-<주제>/DESIGN.md` 를 쓰고 (`.claude/skills/work/references/plan-template.md`) 묻지 않고 Step 3 으로
   - 진행 상황·문제 정의·현재 동작(`file:line`)·해결 방향을 담는다
   - 접근법이 갈려 사용자가 골라야 하면 그 질문을 승인 ① 에 싣는다 (따로 묻지 않음)

## Step 3 — PR 분리

`pm-code-agent` 를 호출한다. 프롬프트에 DESIGN.md 전문과 프로젝트의 PR 분리 기준(추가 파일)을 넣고,
"Rule 3 대신 이 기준을 쓰고, 파일 수·diff 임계치는 무시하라" 고 명시한다.

PR 분리 기준의 공통 틀 (우선순위 순, 구체 예는 프로젝트 추가 파일):

1. 배포 순서가 있으면 분리 — <계약> 변경은 읽는 쪽 선배포
2. 배포 경로·검증 경로가 다르면 분리
3. 경계를 넘어 강결합이면 묶음 — 양쪽 계약을 동시에 바꾸는 경우
4. 크기는 "30분 안에 리뷰 가능한가" 만 본다

이슈 요약·작업 그림·Brainstorm(문제 정의·가정·해결 방향)·PR 분리안을 한 답에 보인다 (승인 ①).

- 접근법이 갈려 사용자가 골라야 할 때만 묻는다 — 그 질문 하나. 분리안은 권장 방향 기준으로 보인다
- 접근법이 하나뿐이면 묻지 않고 Step 4 로 (방향이 틀렸으면 사용자가 보고 끊을 수 있게 그림·표는 그대로 보인다)
