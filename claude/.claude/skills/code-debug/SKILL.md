# Code Debug — 체계적 디버깅

버그의 **root cause를 먼저 찾고**, 증거 기반으로 수정합니다.

> **Iron Rule**: root cause 파악 없이 수정 시도 금지. 증상 수정은 실패다.

## 묻는 기준

- **직접 확인할 수 있는 것은 묻지 않는다.** 재현 여부는 테스트를 돌려서, 발생 시점은 `git log`·`git blame` 으로 확인한다. 사용자에게 되묻는 것은 둘 다 실패했을 때뿐이다
- **선례가 있으면 묻지 않는다.** 과거에 같은 증상을 고친 커밋이 있고 재현 테스트가 가설을 증명하면, 그대로 고치고 **결정 표**(원인 / 선례 커밋 / 증명한 테스트)만 보인 뒤 진행한다
- 묻는 것은 이 넷뿐이다
  - 재현도 못 하고 발생 시점도 못 찾은 경우
  - 선례가 없고 가설이 2개 이상 남은 경우
  - 수정이 **설계 결정**을 건드리는 경우 (계약 변경, 의존 방향, 공개 API)
  - 3회 실패 규칙에 걸린 경우
- 그 외는 묻지 않고 고친다. 고친 뒤 결과를 보고한다

## Step 1: 증거 수집

$ARGUMENTS에서 증상을 파악한 후, 다음을 **병렬로** 수집한다:

### Agent A: 에러 분석 (Explore)

Agent tool (subagent_type: Explore):

```
다음 에러/증상을 분석하세요:
[에러 메시지 또는 증상]

수행:
1. 에러 메시지/스택트레이스 전문 읽기 — 파일, 라인, 에러 코드 추출
2. 해당 파일:라인의 코드 읽기
3. 호출 체인 역추적 — 에러 발생 지점에서 호출자를 따라 올라가기
4. 관련 타입/인터페이스 확인

출력:
  ## 에러 위치: [file:line]
  ## 호출 체인: [caller → callee → error]
  ## 관련 코드 스니펫
  ## 초기 소견
```

### Agent B: 변경 추적 (Explore)

Agent tool (subagent_type: Explore):

```
최근 변경사항과 버그의 연관성을 분석하세요:

수행:
1. git log --oneline -20 — 최근 커밋 확인
2. git diff HEAD~5 --name-only — 최근 변경 파일
3. 변경 파일 중 에러 관련 파일 식별
4. git blame [에러 파일] — 문제 라인의 최근 변경자/시점

출력:
  ## 최근 변경 파일
  ## 에러 관련 변경 이력
  ## 의심 커밋: [hash] [message]
```

## Step 2: 재현 확인 (직접)

**묻지 않고 직접 확인한다.**

1. **재현** — 관련 테스트·빌드 명령을 실제로 돌린다. 실패 로그 전문을 남긴다
   - 테스트가 없으면 증상을 그대로 찍는 최소 명령을 만들어 돌린다
2. **발생 시점** — Agent B 의 `git log`·`git blame` 결과에서 의심 커밋을 특정한다
3. 증거를 한 묶음으로 보인다 (묻지 않는다)

   ```
   재현: <명령> → <실패 메시지 한 줄>
   시점: <hash> <message> 이후 (`git blame` file:line)
   유력 원인 영역: <영역>
   ```

**둘 다 실패했을 때만** AskUserQuestion 으로 묻는다 — 재현이 안 되고 의심 커밋도 못 찾은 경우. 이때 추가 로깅·계측 코드를 제안한다.

## Step 3: 패턴 비교 + 선례 탐색

에러 영역이 확인되면, **동작하는 코드**와 **과거의 같은 수정**을 함께 본다.

공간축 — 동작하는 코드와 비교:

1. **유사 동작 코드 탐색** — Grep으로 같은 패턴/API를 사용하는 다른 코드 찾기
2. **차이점 식별** — 동작하는 코드와 깨진 코드의 차이 목록화
3. **의존성 확인** — 설정, 환경, 외부 시스템 계약

시간축 — 과거에 같은 증상을 어떻게 고쳤는지:

4. **선례 탐색**
   - `git log --oneline -20 -- <깨진 파일>` — 이 파일의 수정 이력
   - `git log -S'<핵심 식별자>' --oneline` — 그 심볼이 들어오고 나간 커밋
   - `git log --grep='<에러 키워드>' --oneline` — 같은 증상을 적은 커밋 메시지
5. **선례 판정** — 찾은 커밋이 **같은 원인**인지 확인한다. 커밋 diff 를 읽고, 지금 증상과 원인이 같은지 본다. 파일만 같고 원인이 다르면 선례가 아니다

## Step 4: 가설 확정

**묻지 않고 진행하는 조건** — 셋을 모두 만족할 때:

- Step 3 에서 **같은 원인의 선례 커밋**을 찾았다
- Step 2 의 재현 명령이 그 가설을 **증명**한다 (가설대로면 실패하고, 아니면 실패하지 않는다)
- 수정이 설계 결정을 건드리지 않는다 (계약·의존 방향·공개 API 불변)

이때는 결정 표만 보이고 Step 5 로 바로 간다:

```
원인: <root cause> (file:line)
선례: <hash> <message>
증명: <재현 명령> → 이 가설대로면 실패
수정: <최소 변경 한 줄>
```

**묻는 경우** — 위 조건 중 하나라도 어긋나면 AskUserQuestion 으로 제시한다:

```
## 가설

**원인**: [구체적 root cause] (file:line)
**근거**: [증거 1], [증거 2]
**영향 범위**: [이 원인이 영향을 미치는 다른 곳]
**선례**: [찾은 커밋 또는 "없음"]

⭐ 추천 수정 방향: [최소 변경 제안]

진행할까요?
```

가설이 2개 이상 남으면 각각을 선택지로 내고, 각 가설을 가르는 **구분 실험**을 함께 적는다.

## Step 5: 최소 수정

핵심 원칙:

- **한 번에 하나만 변경** — 여러 수정을 묶지 않음
- **root cause 수정** — 증상이 아닌 원인을 고침
- **최소 변경** — "ついでに" 개선 금지

수정 후 관련 테스트/빌드를 실행하여 검증한다.

## Step 6: 검증 + 결과

```
## Code Debug — 결과

### Root Cause
[file:line] — [원인 설명]

### 수정 내역
- [file:line] [변경 내용]

### 검증
- 재현 테스트: ✅/❌
- 기존 테스트: ✅/❌

### 다음 단계: /github-ship
```
