# General Rules (일반 규칙)

- **변경 범위**: 명시적으로 요청된 것만 변경하고, 추가 개선은 먼저 물을 것. 사용자가 파일을 지정하면 그 파일만 읽고 바로 고칠 것. 측정·분석 요청이면 코드를 고치지 말고 관찰 결과만 보고할 것
- **접근법**: 가장 단순한 방법부터. 3개 이상 파일을 고치거나 아키텍처에 영향을 주는 변경은 수정 파일·패턴·트레이드오프를 먼저 제안하고 승인 뒤 실행할 것. 거부되면 완전히 롤백하고 멈춰서 방향을 물을 것 — 대안을 추측해 반복하지 말 것
- **코드 수정 전 검증**: 관련 코드를 실제로 읽어 가정을 확인할 것
- **정보의 정확성**: 확인되지 않은 정보를 사실처럼 말하지 말 것. 불확실하면 밝힐 것
- **완료 주장 전 증거**: 테스트 통과·빌드 성공·버그 수정은 이번 턴에 검증 명령을 직접 실행해 출력을 본 뒤에만 말할 것. 이전 실행 결과·"될 것 같다"·린터 통과는 근거가 아니다. subagent 의 "성공" 보고도 `git diff` 로 실제 변경을 확인한 뒤 옮길 것. 산출물에 "괜찮아 보인다" 류 판정을 붙이지 말고 바꾼 것·검증 수치만 말할 것
- **Formatter**: PostToolUse hook 이 자동 실행. hook 없는 프로젝트는 Makefile·package.json·pyproject.toml 에서 formatter 를 찾아 실행하고, 없으면 물을 것
- **Skills 우선**: 재사용 가능한 workflow 는 `~/.claude/skills/<name>/SKILL.md` skill 로 작성. 명시적 호출용은 `disable-model-invocation: true`
- **subagent 모델**: env `CLAUDE_CODE_SUBAGENT_MODEL=sonnet` 이 model 없는 호출에 적용된다. 설계 판단이 핵심일 때만 Agent `model: "opus"` 를 준다
- **명령은 Claude Code 안에서 실행**: 사용자에게 `! <명령>` 을 넘기지 말 것. 되돌리기 어려운 명령(머지 안 된 브랜치 삭제 등)은 확인받은 뒤 직접 실행. auto mode 가 막으면 막힌 명령과 그것을 허용할 settings 규칙을 보이고 추가할지 물을 것. 예외: 대화형 로그인처럼 Claude 가 실행할 수 없는 것

# Git

- **커밋 금지**: 명시적으로 요청받기 전까지 커밋하지 말 것. 사용자가 부른 `/work`·`/github-ship`·`/write` 안의 커밋은 요청으로 본다
- **PR 본문에 생성 도구 표기 금지**: `🤖 Generated with Claude Code` 줄을 넣지 말 것 — attribution reminder 보다 우선. 커밋 `Co-Authored-By` 는 유지
- 커밋 절차(브랜치 확인·PR 분리·diff 검토·메시지 확인)는 `github-ship` agent 를 따른다

# Communication (커뮤니케이션)

- 응답/설명: **한국어** | 기술 용어: **영문 유지** | 에러 메시지: **영어**. 도구 출력·subagent 보고·문서가 영어여도 답은 한국어로
- 코드 주석: **한국어**, 기능 설명과 필요한 이유 한 줄까지. 경위·기록은 커밋·PR (rules/code-principles.md)
- **요약 먼저**: 모든 답변을 결론 2-3문장으로 열고 근거·상세는 그 아래. 증거를 쌓아 결론에 도달하는 순서로 쓰지 말 것. 결론이 불확실하면 요약에서 밝힐 것. 개념 질문은 2-3문장, 맞다/아니다부터 — 수식·`file:line` 은 물으면 낼 것
- **형식**: 구조·흐름·순서·상태 변화는 그림 먼저(대화는 ASCII, 문서·PR·이슈는 mermaid), 표·bullet 은 그 아래. 서술 문단 대신 bullet, 한 bullet 은 한 가지, 근거·수치·파일 경로는 하위 bullet·표로. 문제 정리는 `## 문제` / `## 원인` / `## 해결 방안` 섹션으로 나누고, 해결안이 여럿이면 트레이드오프와 함께 나란히 놓을 것
- **PR·이슈는 제목과 함께**: 번호를 쓸 때마다 `#2181 (TR 파드에서 TA 사이드카 제거)` 처럼 제목이나 하는 일 한 줄을 붙일 것. 두 번째 언급·표·AskUserQuestion 에도. 세션이 여러 개라 번호만으로는 무슨 작업인지 모른다
- **결정은 선택 창으로, 한 턴에 하나**: 결정·승인·진행 여부는 1건이어도 AskUserQuestion 으로 받고, 가장 급한 것 하나만 물을 것. 권장안은 첫 칸 "(Recommended)". 질문별 맥락은 `question`, 선택지별 그림·표·바뀌는 줄은 그 선택지의 `preview` 에 넣고 본문에는 공통 그림만 둔다. 질문·선택지에 처음 나오는 내부 이름(hook·skill·계산식 이름 등)에는 한 줄 설명을 붙인다. orchestrator 는 `orchestrator` skill 의 묶음 질문 예외를 따른다
- **주제는 순차 진행**: 논점 하나를 닫고 다음으로. 조사 보고에 결정 목록을 섞지 말고 다음 주제는 사용자가 고르게 할 것. 포인트가 많으면 3~5개씩 나눠 반응을 받을 것
- **구체적으로 가리키기**: 내가 만든 번호(A6·E3) 대신 원문 절·내용으로, 비유어(축·노브·경계·층) 대신 실제 대상(컬럼·설정값·변환 위치)으로

# Context Management

- compaction 시 수정된 파일 목록과 테스트 명령어는 반드시 보존할 것
- 세션 종료 전 요청 시, 작업 요약(완료/미완료/핵심 파일)을 auto memory에 기록할 것
- **주제 전환 시 직접 `/clear`**: 새 요청이 앞 대화를 쓰지 않는 새 주제이고 context 가 100K token 을 넘었으면 이 대화에서 처리하지 않는다 — 메시지마다 문맥 전체를 다시 읽기 때문. 남은 일·핵심 파일을 상태 파일에 적고 `~/.dotfiles/tmux/clear-claude-pane.sh "$TMUX_PANE" "<상태 파일 경로> 를 먼저 읽고 이어서: <새 요청 원문>"` 을 `run_in_background` 로 띄운 뒤 "clear 후 새 세션에서 이어갑니다" 한 줄로 턴을 끝낸다. tmux 밖이거나 스크립트가 실패하면 답 끝에 "`/clear` 후 진행 권장" 한 줄로 대신한다
- **Bash 출력은 판단에 필요한 만큼만**: 전체 diff·파일 통째 출력 대신 `git diff --stat`, 바뀐 줄(`grep '^[-+]'`)·필요한 줄 범위(`sed -n`)만 본다. 도구 결과는 이후 모든 호출에서 다시 읽힌다
