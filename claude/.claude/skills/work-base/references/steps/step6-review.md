## Step 6 — Review (PR 마다)

`git diff --name-only <base>..HEAD` 로 경로를 보고, 프로젝트 추가 파일의 경로→리뷰어 표에서 해당 리뷰어만 **병렬** 호출한다. 한 PR 이 여러 경로를 건드리면 해당 리뷰어를 모두 병렬로.

프롬프트: plan 경로, PR 번호, base 커밋, **마무리 검증 로그 경로들**(precheck 포함), `<규칙 파일>`(있으면). precheck 가 이미 잡은 항목은 다시 지적하지 않게 한다.
리뷰어는 로그에 있는 검사를 다시 돌리지 않는다. 로그에 없는 것(race·sanitizer·feature 빌드 등 체크리스트가 요구하는 것)만 돌린다.
보안 민감 변경(인증·secret·암호·외부 입력 파싱 — 구체 목록은 프로젝트 추가 파일)이면 global `security-reviewer` 를 추가한다.

같은 라운드에 `code-reviewer` 도 **병렬로** 띄운다. 단 `git diff --shortstat <base>..HEAD` 의 추가+삭제가 50줄 이하면 `code-reviewer` 는 띄우지 않고 경로별 리뷰어만 부른다 (토큰 절감 — 머지 PR 40개 중 24개가 50줄 이하). 보안 민감 변경의 `security-reviewer` 는 크기와 상관없이 붙인다. ship 때는 Claude 리뷰를 다시 돌리지 않는다 (Step 8 `--no-review` — codex 리뷰만 돈다).

- 관점은 고정 3개 + 조건부 (규칙 준수 관점은 precheck·언어 체크리스트와 지적이 겹쳐 뺐다)
  - 버그 — 로직 오류·edge case·nil/null, 불변식을 코드로 따라가 확인
  - 설계 — 모듈 경계·의존·공개 API 모양·다음 PR 이 쓰기 좋은 API (PLAN 의 다음 PR 표를 함께 넘긴다)
  - 테스트 — **변이 방식이 표준**: 새 분기·조건 표·자기 변이 로그를 보고, 살아남을 만한 변이를 직접 건다. PR worktree 는 고치지 않는다 (overlay 나 임시 worktree `git worktree add --detach <tmp> HEAD` 에서 걸고 끝나면 제거, 끝에 `git status` 빈 것 확인). 살아남은 변이만 지적
  - 보안 (외부 입력 파싱·토큰·URL·인증·암호를 바꿀 때만) — **실측 요구**: 프로브를 overlay·임시 worktree 에서 돌려 결과로 지적
  - 성능 (지연·메모리가 쟁점일 때만 — 이슈 AC·PLAN 에 조건이 있거나 사용자가 물을 때. 요청 경로를 바꿨다는 이유만으로는 띄우지 않는다) — **실측 요구**: 벤치·측정을 overlay·임시 worktree 에서 돌려 수치로 지적
  - 형제 일관성 (경로 리뷰어가 붙을 때만, 아래) — 바뀐 코드를 비슷한 이웃 코드·대응 파일(같은 디렉토리의 형제 구현, 다른 플랫폼·언어의 같은 기능, 짝을 이루는 스키마·설정)과 대조해 이름·스키마·에러 처리·순서가 어긋나는 곳을 지적. 대조한 파일 경로를 지적마다 적는다
  - 프로젝트 추가 관점이 있으면 프로젝트 추가 파일대로
- 경로 리뷰어(경로→리뷰어 표의 리뷰어, `security-reviewer`·`database-reviewer` 포함)가 하나라도 붙는 PR 은 관점을 버그·형제 일관성 2개로, 추가+삭제 300줄 초과면 설계를 더해 3개 (경로 리뷰어와 체크리스트가 겹친다 — 관점 지적의 24% 가 같은 파일 ±3줄을 경로 리뷰어도 지적). 테스트·설계 조건은 아래 표보다 이 줄이 우선한다
- 경로 리뷰어가 없는 작은 PR 은 관점을 한두 개로 (토큰 절감 — 리뷰 에이전트가 PR 당 5개·각 120k~220k 이던 일): 추가+삭제 50줄 초과 300줄 이하면 버그 1개, 새 분기·조건 표가 있으면 테스트를 더해 2개. 설계는 다음 PR 이 이 PR 의 API·계약을 쓰거나 공개 API 를 바꿀 때만 더한다. 300줄 초과는 버그·설계 2개에, 새 분기·조건 표가 있을 때만 테스트를 더한다 (테스트 관점이 가장 오래 걸렸다 — 10일 82회 12.4h, high 2건)
- 호출 effort (토큰 절감): 버그 관점은 정의값(`high`) 그대로, 설계·테스트·형제 일관성 관점은 Agent 호출에 `effort: "medium"` 을 준다. 보안·성능 관점은 정의값
- 신뢰도 75 필터는 `~/.claude/agents/github-ship.md` Phase 4 를 따른다
- 프롬프트: diff 범위 `<base>..HEAD`, worktree 경로, 관점 1개, 마무리 검증 로그 경로들(precheck·selfmut 포함)
- 보고 형식은 경로별 리뷰어와 같게 요구한다: 맨 위 `판정: PASS | NEEDS ATTENTION | FAIL` (FAIL = critical/high 1건 이상, NEEDS ATTENTION = medium 이하만), 지적은 `[critical|high|medium|low] file:line`, PR 이 바꾸지 않은 줄이면 끝에 `(범위 밖)`
- `code-reviewer` 프롬프트에 넣는다: "agent-memory 에 쓰지 않는다 (Self-Evolution Protocol 생략). 읽기는 MEMORY.md 색인에서 이번 diff 와 맞는 항목만" (토큰 절감 — 3일 159회에 쓰기 301회·읽기 551회)
- 모든 리뷰어·implementer 프롬프트에 넣는다: "보고는 마지막 메시지 하나로만. SendMessage 로 같은 보고를 따로 보내지 않는다" (같은 보고가 두 번씩 오던 문제)
- 지적을 받으면 반영 lane 에 넘기기 전에 메인이 리뷰어 사이 중복을 합친다 (같은 지적은 한 줄, 낸 리뷰어 목록만)
  - 리뷰어끼리 같은 줄에 맞서는 지적을 내면(고쳐라 · 그대로 둬라) 합치지 않고 아래 재확인으로 가른다

FAIL·NEEDS ATTENTION 이 있으면 (묻지 않고 진행):

- PR 이 바꾼 줄에 대한 지적은 등급과 상관없이(critical~low) **반드시** 고친다. 사용자에게 고칠지 묻지 않고, "사소함·취향·후속 PR 로" 를 이유로 넘기지 않는다. 지적마다 Task 를 추가하거나(동작 변경 → 실패 테스트부터) 기존 Task 를 보강. 지적끼리 파일이 겹치지 않으면 lane 을 나눠 병렬
  - low 는 지적마다 lane 을 띄우지 않고 그 라운드의 low 전부를 fix lane 1개에 묶어 한 번에 고친다 (지적 78% 가 low 라 fix 호출이 새 lane 보다 많았다)
  - 고치지 않는 경우는 아래 두 줄(범위 밖 · 설계 결정 필요)뿐이다. 그 밖의 지적을 안 고쳤으면 Step 8 로 가지 않는다
  - 리뷰어가 낸 지적이 코드 관점에서 틀렸으면(재현·근거로 반박 가능) 고치지 않고 근거를 Step 7 표에 적는다 — "안 고침: <지적> · 근거 <file:line·실행 결과>"
    - 안 고치기 전에 재확인: Agent(`model: "opus"`, `effort: "high"`) 하나에 지적 원문·반박 근거·해당 diff hunk 만 넘겨 `고침 / 안 고침` 과 근거 한 줄을 받는다. 리뷰어 간 충돌도 같은 방식. 판정이 고침이면 고친다
- `(범위 밖)` 지적은 고치지 않고 PR 본문 범위 밖 절에 적는다
- 고치려면 설계 결정이 필요한 지적(다른 이슈 계약·<계약> 호환·규칙 예외)은 고치지 말고 `## 결정 대기` 에 쌓는다 (끝: 결정 모음에서 묻는다)
- 고친 뒤: 바뀐 모듈의 마무리 명령만 다시 + precheck → 재리뷰는 **critical·high 지적을 고친 반영분만, 그 지적을 낸 리뷰어에게, 반영 커밋 diff(`<리뷰한 HEAD>..HEAD`)와 그 지적 목록만**
  - medium·low 만 고친 라운드는 재리뷰하지 않는다 (2라운드 이후 리뷰 170회에서 high 이상 2건). 마무리 명령 통과 + precheck error 0 으로 갈음하고 Step 7 표에 "재리뷰 생략: medium·low 반영" 한 줄
  - 테스트 보강 반영은 변이 로그(그 지적의 변이가 이제 죽음)를 남긴다
- 같은 지적이 2회 반복되면 멈추고 사용자와 본다
