# Tracing System Internals

## Overview

**결론의 근거는 코드다. 문서·주석은 출발점이자 검증 대상이다.**

주석은 자기가 낡은 것을 모른다. 주석이 설명하는 설계는 읽되, 그것이 지목한 심볼이
**지금도 그렇게 동작하는지** 확인한 뒤 인용한다.

## 답변과 문서의 형태

| 대상          | 다이어그램        | 이유                               |
| ------------- | ----------------- | ---------------------------------- |
| 터미널 응답   | ASCII 박스·화살표 | mermaid 코드펜스는 렌더되지 않는다 |
| 프로젝트 문서 | mermaid 적극 사용 | 뷰어·Notion 이 렌더한다            |

**낯선 도메인 용어는 처음 쓸 때 한 줄로 정의하고 넘어간다.** 읽는 사람이 그 도메인
엔지니어가 아닐 수 있다. 정의 없이 쓰면 그 문단 전체가 읽히지 않는다.

- ❌ "r_obs 를 EMA 로 스무딩한다"
- ✅ "실측 소진율을 EMA(지수 이동 평균 — 최근 값을 더 무겁게 친 평균)로 스무딩한다"

약어·모델명·통계 기법·도메인 지표가 해당한다. 정의는 **한 줄**이면 충분하고,
깊이는 물어보면 그때 낸다.

**인프라 설명은 진입 경로 그림부터.** LB·Gateway·NAT·IAM 설명은 누가 어디로 들어와 어느
클러스터·리소스에 닿는지 ASCII 그림부터 보이고, 용어는 첫 등장 시 한 줄로 푼다 (사용자는
인프라 배경이 얕다).

## 출발점 확인

- **docs 는 출발점, code 가 근거**: repo `docs/` 로 지도를 잡되, 결론은 반드시 코드·설정 파일
  (디렉토리 트리, go.work, Cargo.toml, Helm values, package.json)로 검증한다. 문서 내용을 그대로
  사실로 옮기지 않는다
- **문서의 작성 기준 먼저 확인**: `git log -1` 로 체크아웃 시점을,
  `git for-each-ref --sort=-committerdate refs/remotes/origin | head` 로 활성 브랜치를 확인한다.
  기본 브랜치가 활성 브랜치가 아닌 경우가 있고(main 은 죽고 develop 이 활성), 문서가 자기
  스테일니스를 모르는 경우도 있다. git 추적 여부(`git status`)로 팀 공식 문서와 로컬 생성물을
  구분한다

## 탐색 체크리스트

| 찾는 것         | 흔한 실패                                                    | 대응                                                                                                                                     |
| --------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 호출부          | `.Method(` 만 grep → 주입된 함수 타입·인터페이스 구현을 놓침 | `LSP` 도구 `findReferences`·`incomingCalls`·`goToImplementation` 먼저. 안 되면 타입명(`XxxFunc`)·필드명·wrapper 이름으로 다시 grep       |
| 설정 기본값     | 코드 기본값과 배포 기본값을 혼동                             | 코드(필수 ENV·`Default` impl)와 차트/매니페스트 default 를 각각 확인                                                                     |
| 주기·임계       | 한 값에서 여러 동작이 유도되는지 모름                        | 그 상수를 참조하는 **모든** 지점을 grep                                                                                                  |
| 설계 근거 주석  | 주석이 낡음                                                  | 지목된 심볼의 실제 호출자를 역추적                                                                                                       |
| §번호·문서 참조 | 이 레포에 없는 문서일 수 있음                                | 레포 내 존재를 먼저 확인. 없으면 같은 결정 번호(예: `BP-D2x`)를 코드 전체에서 grep 해 주석으로 의도를 복원하고, 소재는 작성자에게 묻는다 |

**grep 한 번으로 "호출부 없음"을 단정하지 않는다.** 함수 타입 주입, 인터페이스 구현,
메트릭 wrapper 를 거치면 호출부의 문자열 모양이 달라진다. "없다"고 말하기 전에
**심볼의 타입 정의부터 찾아 그 타입명으로 다시 검색**한다.

**Go·Rust·TS·Python 의 정의·참조·구현체는 `LSP` 도구로 먼저 찾는다.** 문자열이 아니라 타입으로
찾아서 주입된 함수 타입·인터페이스 구현도 잡힌다 (`ToolSearch` 로 `select:LSP` 를 먼저 불러온다).

- 쓸 동작: `findReferences`(사용처), `goToImplementation`(인터페이스 구현체), `incomingCalls`/`outgoingCalls`(호출 계층), `goToDefinition`, `workspaceSymbol`(이름으로 심볼 찾기, `query` 필수)
- 위치는 1-based `line`·`character` 로 심볼 이름 위를 가리킨다. 줄은 `documentSymbol` 이나 grep 으로 먼저 찾는다
- 첫 호출은 인덱싱 전이라 0건이 나올 수 있다. 한 번 더 부르기 전에는 "참조 없음" 으로 단정하지 않는다
- 언어 서버의 workspace 는 세션 작업 디렉토리다. 다른 저장소의 파일은 참조를 못 찾으므로, 그 저장소에서 연 세션에서 쓰거나 grep 으로 대신한다
- 언어 서버가 없다는 오류(`Executable not found`)가 나면 grep 으로 돌아가고 그 사실을 보고에 적는다

```
# 부족 — 호출부가 있어도 안 잡힌다
grep -rn "\.Confirm(" services/

# 충분 — 주입 타입·필드·wrapper 까지
grep -rn "Confirm" services/ | grep -v _test
```

## 파악한 내용을 어디에 두나

| 내용                    | 위치                                                         |
| ----------------------- | ------------------------------------------------------------ |
| 확정된 이해             | 컴포넌트 문서 (`docs/components/<name>.md` 등 프로젝트 관례) |
| 코드와 어긋난 주석·이름 | 같은 문서의 "어긋나는 지점" 표 — 근거 `file:line` 과 함께    |
| 손댈 부채               | 별도 이슈 초안 문서. 확인 전 사실은 "남은 확인"으로 명시     |

문서에는 **왜 그런가**를 남긴다. 무엇을 하는지는 코드가 이미 말한다. 주석에 장애·이슈
번호가 있으면 함께 옮긴다 — 그 설계를 되돌리려는 다음 사람을 막는 것은 결론이 아니라 근거다.

## Common Mistakes

- **문서 내용을 근거로 제시** → 코드 인용(`file:line`)으로 대체한다
- **한 번의 grep 으로 부재를 단정** → 타입·wrapper 경로를 확인하기 전엔 "확인 못 함"으로 답한다
- **개념이 코드에 없다고 "없음" 단정** → `gh issue list --state all --search '<용어>'` (한글·영문)로 이슈도 본다. 미구현 개념은 이슈에만 있다
- **용어를 정의 없이 사용** → 첫 등장 시 한 줄 정의
- **터미널에 mermaid 출력** → ASCII 로 그린다
- **틀린 답을 조용히 덮어쓰기** → 앞서 말한 것이 틀렸으면 무엇이 틀렸는지 한 줄로 밝히고 넘어간다
