# design-doc

설계 문서는 처음 읽는 사람이 목차만 보고 컴포넌트를 찾아가,
**무엇이 바뀌고 · 어떻게 돌고 · 왜 그렇게 정했고 · 무엇이 남았나** 를 한 곳에서 읽는 문서다.

```
① 뼈대 맞추기 ─▶ ② 자리 정하기 ─▶ ③ 쓰기 ─▶ ④ 검사 (lint · 읽기) ─▶ ⑤ 후처리
```

형식만 맞추고 끝내지 않는다. lint 0 은 형식이 맞다는 뜻일 뿐이다.
문장을 옮기고 쪼개는 것만으로는 구조가 바뀌지 않는다 — 뼈대와 틀에 맞춰 **다시 쓴다**.

## ① 뼈대 맞추기

```
# 제목 · 머리말 (상태 · 기준 리비전 · 영향 범위)
## 목차          ← ##·### 두 단계
## 0. 목표       ← 3~5줄. 무엇을, 범위, 성공 기준. 구조 설명은 쓰지 않는다
## 1. 흐름       ← API·시나리오별 그림과 순서만
## 2. 컴포넌트   ← ### 컴포넌트 하나 = 아래 틀
## 3. WBS
## 4. 결정·고민 사항 ← 고민·결정·확인 ###
## 용어
```

컴포넌트 틀 — `### 2.N <컴포넌트>` 아래:

| 소제목             | 담는 것                                              |
| ------------------ | ---------------------------------------------------- |
| `#### 바뀌는 것`   | 지금 대비 새로·바뀜 2~3줄                            |
| `#### 동작`        | 그림 → 표 → bullet                                   |
| `#### 결정과 이유` | 결정마다 "결론 — 이유" 1줄. 표는 3행 이하일 때만      |
| `#### 미정`        | 질문 절 분류·주제만 ("결정 — floor 기준")              |

- 해당 없는 소제목은 뺀다. 바뀌는 게 없으면 `바뀌는 것: 없음` 한 줄로 끝낸다
- 컴포넌트 하나는 20줄 이하 (그림 제외), 문서 전체는 500줄 이하. 넘으면 명세는 WBS 항목 토글·이슈로, 근거는 decision-log 로
- 맨 위에 `명세: #N` 처럼 명세가 있는 곳을 한 줄로 (`references/rules.md` `## 문서 계층`)
- 컴포넌트는 `###` 한 단계로 나란히 둔다. 묶음(`### 서버` → `#### API`)을 두면 틀이 다섯 단계로 내려간다
- 자세한 형식은 `references/rules.md`

## ② 자리 정하기

쓰기 전에 문장마다 자리를 정한다. 한 사실은 한 곳에만 둔다.

| 내용                                    | 자리                                                      |
| --------------------------------------- | --------------------------------------------------------- |
| 호출 순서 — 누가 누구를 언제 부르나     | §흐름                                                     |
| 규칙·값·예외 — 무엇을, 어떻게           | 그 컴포넌트의 `동작`                                      |
| 왜 — 결론과 한 줄 이유                  | 그 컴포넌트의 `결정과 이유`                               |
| 왜 — 비교한 안 전체, 근거 분석, 대가    | `decision-log.md`                                         |
| 명세 — 필드·컬럼·코드표·예시·구현 주의점 | WBS 항목 토글(이슈 없을 때) 또는 GitHub 이슈              |
| 아직 안 정한 것, 남에게 물을 것, 가정   | §질문 (컴포넌트 `미정` 엔 이름만)                         |
| 언제·무엇에서 바뀌었나, 정정, 결정 날짜 | `decision-log.md` 만                                      |
| 파일 경로·함수명·필드 번호·ENV          | WBS 항목 (결정 근거 `file:line` 은 `결정과 이유` 에 둔다) |

- 흐름과 컴포넌트가 겹치면 컴포넌트에 두고 흐름에서 지운다
- 사용자의 "~하면 어때요?" 는 결정이 아니다. 승인 전에는 §질문의 내부 안건으로만
- 결정을 바꾸면 옛 문장을 고쳐 쓴다. "→ 바꿈" 을 덧붙이지 않는다. 옛 안은 `결정과 이유` 의 비교한 안 한 행

## ③ 쓰기

`references/rules.md` 를 따른다. 자주 어기는 것:

- 본문에 결정 날짜를 쓰지 않는다 (`(2026-10-11)`, `(10-07 확인)`)
- 한 줄 90자 이내 (표·코드 제외). 넘으면 하위 bullet
- 절 안 순서: 그림 → 표 → 문장 bullet
- 길 안내 문장("맨 아래 참고") 금지, 비유어(축·노브·경계·층) 금지
- 토글은 WBS 항목 상세와 질문 절에만. 본문에서 접고 싶을 만큼 길면 WBS 토글·이슈·decision-log 로

## ④ 검사

lint — 형식:

```bash
python3 ~/.claude/skills/design-doc/scripts/doc_lint.py <문서.md> [...]
```

- 날짜·경위 문구·질문 표지·90자 초과·길 안내·비유어·`리더십`·깨진 목차 링크·컴포넌트 틀 누락·컴포넌트 20줄 초과·토글·결정 표 3행 초과·문서 500줄 초과를 줄 번호와 함께 낸다
- 경위 문구(기각 등)는 `결정과 이유` 안에서, 질문 표지(확인 필요 등)는 §질문 안에서만 허용
- `decision-log.md` 는 건너뛴다. 걸린 줄을 0 으로 만든다. 오탐이면 그 줄을 사용자에게 보인다
- doc_lint 에 여러 파일을 넘기면 합계가 파일마다 따로 나온다. 보고할 합계는 그 문서를 단독으로 돌려 얻는다

읽기 — 큰 구조를 바꿨거나 사용자가 "읽기 어렵다" 고 했을 때: `references/reading-check.md`

## ⑤ 후처리

- 프로젝트 `CLAUDE.md` 의 문서 후처리가 있으면 따른다
- 결정이 바뀌었으면 decision-log 맨 아래에 경위
- GitHub 이슈에는 설계 문서 절·WBS 번호를 쓰지 않는다. 결정 내용을 옮긴다
- 보고는 절별 줄 수 전·후, lint 수치, 읽기 검사 결과만. 자기 평가는 하지 않는다
