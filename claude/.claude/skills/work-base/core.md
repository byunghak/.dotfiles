## 흐름

사람 판단이 필요한 단계는 이 대화에서, 자동 구간만 agent 에 맡긴다. 아래 `<…>` 는 위 `## 설정` 표의 값이다.

```
준비 → 이슈 분석+작업 그림+Brainstorm+PR 분리 → Plan → [PR 마다: Code → 마무리 검증 → Review → Ship → 머지 → 정리] → 끝: 결정 모음
                     승인 ①*                   승인 ②*       자동        자동          자동     자동    자동**  자동       한 번에
                (큰 작업은 착수 인터뷰)

*  ① 은 착수 인터뷰 조건(Step 3)에 해당하거나 접근법이 갈릴 때만, ② 는 판단 지점·<계약> 변경·PR 2개 이상일 때만 묻는다. 아니면 그림·표만 보이고 진행
*** 독립 PR(depends_on 없음·수정 파일 안 겹침)은 승인 ① 뒤 orchestrator 가 띄운 다른 worker 가 동시에 맡는다 (Step 3 `병렬 착수`)
** base 가 <통합 브랜치> 면 리뷰 통과 뒤 바로 머지. <확인 base> 머지는 DESIGN.md `## 사전 승인` 조건을 채우면 묻지 않고, 아니면 "끝: 결정 모음" 에서 확인받는다. 정리는 머지를 검사로 확인한 뒤 자동
```

원칙 ("작업 흐름을 방해하지 않고, 끝난 뒤 마지막에 한 번에 결정"):

- 진행을 막지 않는 결정은 묻지 않는다. 권장안으로 진행하고 PLAN.md `## 결정 대기` 에 `- <결정> · 고른 값 <권장안> · 근거 · 바꾸면 고칠 곳` 으로 쌓는다
- 진행을 막는 결정(이 값 없이는 다음 Task 를 못 짬 · 되돌리기 어려움: <계약>·다른 이슈 계약)만 그때 묻는다
- 큰 작업은 착수 인터뷰(Step 3)에서 머지·배포·결과 코멘트·후속 PR 착수를 조건부로 미리 받고(`## 사전 승인`), 모르는 것이 나오면 정할 순서(`## 위임 원칙`)를 DESIGN.md 에 적는다
- 진행 중 새 결정: 위임 원칙으로 정해지면 정하고 PR "자체 결정" 절에 적는다. `## 사용자에게 남김` 에 해당하거나 사전 승인 조건이 깨지면 `## 결정 대기` 에 쌓고 그 PR lane 만 멈춘다 — 다른 lane 은 계속
- 끝: 결정 모음에서 쌓인 것을 한 번에 처리한다

## 협상 대상 아닌 규칙

- 실패 테스트(Red 로그) 없이 실제 코드를 바꾸지 않는다. 면제는 이 둘뿐이다: 기존 동작을 고정하는 가드 테스트(Red 에서 통과가 정상, 보고에 "가드" 로 표시), 동작을 바꾸지 않는 변경(주석·문서·설정 값·이름 변경)
- 로그에 SKIP 이 있으면 Red 도 Green 도 아니다
- 승인 단계(위 그림의 승인 ①②)는 묻는 조건에 해당하면 사용자 승인 없이 넘어가지 않는다. 진행 중 질문은 한 턴에 1개
- 자동 단계는 묻지 않고 이어 간다. 진행 중에 묻는 것은 진행을 막는 결정뿐: <계약> 호환 판단, 다른 이슈 계약, 실제 코드의 범위 밖 수정, 같은 지적 2회 반복. 나머지는 `## 결정 대기` 로
- 같은 검사를 두 번 돌리지 않는다. 전체 검증은 PR 마무리에서 1회, 리뷰어는 그 로그를 읽는다
- 커밋은 lane 단위로 implementer 만 한다. push·PR 은 Ship 단계에서 `/github-ship` 만
- 머지는 merge commit(`--merge --match-head-commit <sha>`)으로만. squash·rebase 금지
- <커밋 제외> 는 커밋하지 않는다
- PLAN.md·DESIGN.md 는 Edit·Write 도구로만 쓴다. `cat >> .claude/plans/...` 같은 셸 쓰기 금지 — 상대 경로 셸 쓰기는 권한 승인 대기로 멈춘다 (10일 7건·409분)
- 배경 명령은 완료 알림을 기다린다. `sleep`·`until` 폴링이나 watch 스크립트를 따로 띄우지 않는다 (10일 폴링·watch 대기 약 8h). 원격 CI 대기는 `gh pr checks <PR> --watch` 하나를 배경으로

## 단계별 상세

단계에 들어갈 때 공통 파일을 읽고, 이어서 프로젝트 추가 파일이 있으면 읽는다. 둘이 다르면 프로젝트 추가 파일을 따른다. 이 본문은 흐름과 규칙만 담는다 — compaction 뒤 skill 본문이 다시 붙을 때 크기를 줄이려는 것. compaction 뒤에는 PLAN.md 상태 칸으로 현재 단계를 찾아 두 파일을 다시 읽는다.

- 공통: `~/.claude/skills/work-base/references/steps/<파일>`
- 프로젝트 추가: `.claude/skills/work/references/addenda/<파일>` (없으면 건너뜀)

| 단계       | 파일                 | 하는 일                                                     |
| ---------- | -------------------- | ----------------------------------------------------------- |
| Step 0     | `step0-prepare.md`   | 입력 판별·빠른 경로·`<BASE>` 최신화·worktree·controller     |
| Step 1~3   | `step1-3-analyze.md` | 이슈 분석·작업 그림·Brainstorm·PR 분리·착수 인터뷰 (승인 ①) |
| Step 4     | `step4-plan.md`      | `<planner>`·`<plan-reviewer>` (승인 ②)                      |
| Step 5·5.5 | `step5-code.md`      | lane 별 `<implementer>`·마무리 검증                         |
| Step 6     | `step6-review.md`    | 경로별 리뷰어·관점·지적 반영                                |
| Step 7·8   | `step7-8-ship.md`    | Ship 판단·`/github-ship`                                    |
| Step 9·끝  | `step9-merge-end.md` | 머지·정리·결정 모음                                         |
