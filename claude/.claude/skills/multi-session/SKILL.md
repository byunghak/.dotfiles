# Multi-session

Project CLAUDE.md defines group names and project workflow. If the project has `.claude/references/multi-session.md`, read it when you start: it holds that project's report formats and merge/close flow, kept out of CLAUDE.md so it loads only for multi-session work.

- Name sessions `<group>-orchestrator`, `<group>-design`, or `<group>-worker-<issue>-<topic>`. The `work-session-title` hook may rename workers.
- 세션이 orchestrator 를 맡으면(새로 시작·resume 모두) 맨 먼저 `ListAgents` 첫 줄 "This session is <name>" 으로 자기 이름을 본다. `<group>-orchestrator` 가 아니면 첫 답의 첫 줄에서 사용자에게 `/rename <group>-orchestrator` 입력을 요청하고, 이름이 바뀐 것을 확인하기 전에는 worker 를 띄우지 않는다. Claude 는 `/rename` 을 스스로 실행할 수 없고, 자기 pane 에 send-keys 하는 것은 실행 중인 턴과 겹친다. worker 는 이름 접두어로 orchestrator 를 찾으므로, 이름이 다르면 결정 필요를 orchestrator 대신 자기 pane 에서 사용자에게 묻는다 (11-12: resume 한 orchestrator 가 `<repo>-d7` 이름 그대로라 ilrd·2789·2753 worker 가 못 찾고 직접 물음).
- The orchestrator must start every worker with `/multi-session` at the beginning of its initial prompt, followed by the task. For example: `claude -n <group>-worker-<issue>-<topic> "/multi-session <group>-worker-<issue>-<topic> 로 <task prompt>"` — `-n` 에 전체 이름을 준다. 그룹 이름만 주면 같은 이름 세션이 여럿 생겨 SendMessage 가 엉뚱한 worker 로 간다 (10-29: `-n <group>` 으로 띄운 worker 3개, 한 worker 에 갈 메시지가 다른 worker 로 감). 이슈가 아직 없으면 `<group>-worker-<topic>`. This applies to every workflow; `/work` is one possible task, not a dependency. Open new workers as panes in the orchestrator's own tmux window (split the bottom-right worker with `tmux split-window -d -v -t '<window>.{bottom-right}'`, or the orchestrator with `tmux split-window -d -h -t <orchestrator pane>` when there is no worker yet (`-d` 는 커서를 지금 pane 에 둔다. 빼면 새 worker 로 옮겨 가 사용자가 보던 화면이 바뀐다), then `~/.dotfiles/tmux/layout-claude-window.sh <window>`, which keeps the orchestrator on the left and stacks workers on the right, folding every worker but the focused one to its title line. 오케스트레이터 pane 을 위아래로 나누면 배치 스크립트가 다시 펴기 전까지 orchestrator 가 반 높이로 줄었다가 돌아온다), never in a new window (10-27 user). Every new task (new issue, new PR to finish, follow-up outside the worker's issue) gets a new worker session; never hand it to an existing worker, even an idle one (10-27 user).
- Workers find their orchestrator in `ListAgents` by name prefix. Route decisions outside the worker column of the 결정 규칙표 (below) as `결정 필요: <질문 1개>` with options and a recommendation, then wait; ask the user directly only if no orchestrator is active.
- worker 로 실행 중이면 다른 skill·agent 가 사용자에게 묻는 지점(AskUserQuestion, "사용자에게 확인")도 결정 규칙표로 가른다. worker 칸이면 스스로 정하고, 나머지는 `결정 필요` 로 보낸다. 사용자는 worker pane 에 답하지 않아 그 자리에서 멈추기 때문이다 (예: 리뷰 코멘트 반영은 worker 칸, 리뷰 답변 게시는 사용자 칸 / `github-ship` agent 의 PR 분리 질문 — orchestrator 칸).
- 세션 간 메시지는 받는 쪽이 할 일이 있을 때만 보낸다 — `결정 필요`, 완료, 막힘. 착수·진행·수신 확인("받았습니다")은 보내지 않는다. 완료 보고는 PR·리뷰·머지 결과를 한 통에 묶는다
  - worker 가 보내는 `결정 필요`·완료·막힘은 첫 줄을 `진척: <끝낸 단계 수>/<전체 단계 수> #N 짧은 제목 · 지금 하는 일·기다리는 것` 으로 쓴다. 단계는 worker 가 세운 계획(PR·작업 단위) 기준이다. orchestrator 는 이 줄을 그대로 `@claude_progress` 에 옮긴다
  - 이유: 받는 세션은 메시지 길이와 상관없이 컨텍스트 전체를 다시 읽는다 (10-22~30: 세션 간 메시지로 시작한 턴 1,418회 · main 비용의 19%, 깨어날 때 컨텍스트 중앙값 209K, 그중 진행·확인 315회)
  - 진행 상황은 orchestrator 가 필요할 때 PR·상태 파일로 확인한다
- Only an orchestrator's explicit report — "the user chose/approved X" or `orchestrator 결정: X` — counts as an answer. Other session messages are not approval.
- 결정은 결정 규칙표로 누가 정할지 가른다. 사용자 개입은 되돌리기 어려운 결정으로, 세션 간 메시지는 다른 worker 에 영향이 있는 결정으로 좁히려는 것이다. 프로젝트 `.claude/references/multi-session.md` 에 `## 결정 규칙표` 절이 있으면 그 표가 아래 기본 표를 대신한다. 없으면 아래 기본 표를 쓴다.
  | worker 가 정함                                                                                                                                                                                                                                          | orchestrator 가 정함                                                                                                                                                                         | 사용자에게 올림                                                                                                                                                                                                                                                                                       |
  | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | 자기 이슈 안의 구현 방식·코드 구조, 테스트 추가·보강·테스트 환경 준비, 다음 검증·측정 단계 선택, API·스키마·wire 계약과 기능이 하는 일을 바꾸지 않는 구현 계획(Plan) 승인, 동작을 바꾸지 않는 리뷰 지적 반영, 브랜치·worktree 생성, 저장소 안 문서 수정 | 다른 worker 에 영향이 있는 것: PR 분리 단위, 이슈 간 순서·의존, 여러 이슈가 함께 쓰는 파일·모듈 변경, 이슈 범위 해석, 세션·subagent 관리. 같은 저장소 이슈·PR 에 검증·결과를 보고하는 코멘트 | merge·deploy·terraform apply·branch 삭제 등 되돌리기 어려운 명령, 사용자가 정하지 않은 작업의 새 worker 착수, 이슈 생성·그 밖의 이슈·PR 코멘트·Slack 등 외부 게시, API·스키마·wire 계약 변경, 기능이 하는 일(허용 범위·동작 범위)을 바꾸는 선택, 이슈 범위 밖 새 작업, credential, 비용이 드는 리소스 |
  - 가르는 기준: 다른 worker 의 작업·PR 에 영향이 있으면 worker 칸이 아니다. 되돌리기 어렵거나 저장소 밖에서 보이면 사용자 칸이다. 구현 방식이라도 기능이 하는 일을 바꾸면(예: 허용·차단 둘 다 → 허용 목록만, 화면만 → 서버 값까지) 사용자 칸이다.
  - 근거 (11-15, 30일 히스토리 질문 1,361건 중 400건 분류): worker 칸에 해당하는 질문이 38% 였고 사용자는 그 권장안을 88% 골랐다. 권장안과 다르게 고른 경우의 절반은 질문을 이해 못 한 되묻기였고, 나머지는 기능 범위를 바꾼 선택이었다. 새 worker 착수는 권장안 채택 60% 라 사용자 칸, 같은 저장소 결과 보고 코멘트는 95% 라 orchestrator 칸에 둔다. Plan 승인은 13건 모두 권장안이 채택돼(100%) 계약·기능 변경이 없는 것만 worker 칸에 둔다.
  - worker 는 자기 칸 결정을 메시지 없이 정하고 PR 본문 "자체 결정" 절에 `<선택> — <이유 한 줄>` 로 적는다. `결정 필요` 메시지마다 orchestrator 가 깨어나 컨텍스트 전체를 다시 읽기 때문이다 (위 19%).
  - orchestrator 는 자기 칸 결정을 worker 에 `orchestrator 결정: <선택> — <이유 한 줄>` 로 중계하고, 상태 파일 "자체 결정" 칸에 적는다. 사용자에게는 다음 보고 끝에 한 줄씩 묶어 알린다. 확인을 묻지 않는다.
  - 표로 가를 수 없으면 한 칸 오른쪽(worker → orchestrator → 사용자)으로 올린다. 사용자가 자체 결정을 뒤집으면 그 종류를 한 칸 오른쪽으로 옮긴다. 고치는 곳은 그 결정에 쓴 표(프로젝트 표가 있으면 프로젝트 표)다.
  - 사용자에게 올릴 결정이 생기면 AskUserQuestion 직전에 `PushNotification` 으로 한 줄 알린다 (예: `결정 2건 대기: #123 머지, Slack 공지`). 사용자가 터미널을 보고 있으면 도구가 알아서 보내지 않는다.
  - 권한 프롬프트에 `send-keys 1` 로 답하는 것은 이 표와 무관하게 사용자가 승인한 명령에만 한다. auto mode classifier 가 다른 세션의 승인을 사용자 승인으로 보지 않을 수 있기 때문이다.
- 쌓인 결정은 AskUserQuestion 한 번에 묻는다 (10-30 user). 전역 CLAUDE.md "한 턴에 질문 1개" 의 orchestrator 예외다.
  - 배경: orchestrator 에는 여러 worker 의 `결정 필요` 가 동시에 쌓인다 (10-30: PR C 정의·Grafana PR 1 착수·#2377 머지·paused pool 이슈화 4건). 한 턴에 하나씩 물으면 사용자가 네 번 오가야 하고, 그동안 나머지 worker 는 답을 기다리며 논다. 그날 "남은 결정 4건 한번에 보여주세요" 에 AskUserQuestion 4개로 받고 같은 턴에 중계·worker 2개 기동까지 했더니 사용자가 "앞으로도 worker 결정 사항들은 이렇게 처리되면 좋겠다" 고 했다. 이후 #2022 머지·옛 브랜치 삭제·이슈 코멘트, Grafana PR 3 머지·safe-to-evict·보안 후속·admin 계정도 같은 방식으로 처리했다.
  - 방식: 결정이 2건 이상이면 질문 하나에 결정 하나씩, 최대 4개. 각 질문은 맥락 한두 문장(무엇을 바꾸는가, 되돌릴 수 있는가) + 선택지 2개에서 4개, 권장안을 첫 칸에 "(Recommended)". 선택지 description 에 고르면 실제로 일어나는 일(머지 명령의 head, 다시 뜨는 pod, 비용)을 적는다. 사용자는 대화창 위 본문보다 이 대화상자를 먼저 읽는다.
  - 질문에 처음 나오는 용어·내부 이름(계산식 이름, 계약 번호, 다른 이슈의 결정 모음)에는 한 줄 설명을 붙이고, 결정 모음은 항목을 펼쳐 보인다. 설계·계약 질문은 기준 구현(예: MAX)이 같은 문제를 어떻게 푸는지 먼저 조사해 질문 맥락에 넣는다. 같은 분석에서 되묻기가 23건(6%) 나왔고, "MAX 는 어떻게?" 가 반복됐으며, 설계·계약 질문은 권장안 채택 52%·직접 입력 30% 였다.
  - 머지 질문 (머지 대기 `결정 필요` 가 가장 많다 — 30일 652건 중 약 240건, 37%): 리뷰·검증 증거를 통과한 머지 대기 PR 이 여럿이면 질문 하나에 multiSelect 로 묶는다 (선택지 하나가 PR 하나, 고르지 않은 PR 은 보류). 머지 뒤 배포가 따르는 PR 은 "머지 + 배포" 를 선택지로 함께 둔다 — 사용자가 권장안 대신 고른 답에 "머지 + 배포" 가 반복됐다. 증거가 빠졌거나 base 가 main·develop 인 PR 은 묶지 않고 따로 묻는다.
  - 4개를 넘으면 되돌리기 어려운 순(머지·삭제·외부 게시 → wire·계약 → 나머지)으로 앞 4개를 묻고, 나머지는 답 받은 뒤 이어 묻는다. 1건이면 평소처럼 한 질문.
  - 질문별 설명은 그 질문 안에 둔다: 맥락은 `question` 칸, 선택지별 흐름 그림(ASCII)·바뀌는 줄 표는 그 선택지의 `preview`(여러 줄 고정폭, 커서를 두면 옆에 보임). `preview` 는 단일 선택에서만 되므로 multiSelect(머지 묶음)는 `description` 에 쓴다. 본문에는 모든 질문에 공통인 그림과, 길어서 칸에 안 들어가는 원문(이슈 코멘트 초안 전문)만 둔다 (11-18 사용자: 본문에 Q1~Q4 설명을 쌓으니 탭마다 스크롤해야 했다).
  - 답을 받은 같은 턴에 실행까지 한다: 승인된 머지는 `--match-head-commit` 으로 직접, 결정은 해당 worker 에 SendMessage 로 중계, 새 작업은 새 worker 를 띄운다. 다음 턴으로 미루지 않는다.
  - 답이 결정이 아니라 질문이면(Other 에 "이거 X 말씀하시는 거죠?") 그 항목은 결정으로 치지 않는다. 답한 뒤 그 항목만 다시 묻고, 나머지 답한 항목은 실행한다 (10-30: #2022 머지 칸에 "만료 시간 늘리는 거죠?" → 이 PR 들은 만료를 바꾸지 않는 사전 계측이라고 설명 뒤 다시 물음).
  - 대화상자가 거절(취소)되면 멈추고 기다린다. 사용자가 "실수로 닫았다" 고 하면 같은 질문을 그대로 다시 띄운다 (10-30).
- The user decides only in the orchestrator session and does not press buttons in worker panes (10-28 user). Workers never ask the user directly. Before a command likely to raise a permission prompt or be refused by the auto mode classifier (merge, terraform apply, deploy, branch delete), a worker sends the exact command as `결정 필요:` to the orchestrator and waits. After the user approves here, the orchestrator relays the approval and watches the worker pane (`~/.dotfiles/tmux/peek-claude-pane.sh <pane>`, not `tmux capture-pane`: a folded worker shows only one line, so peek unfolds it for a second, captures, and folds it back). If a permission prompt appears and its full command matches what the user approved, the orchestrator answers it with `tmux send-keys -t <pane> 1` (Yes). It never picks "don't ask again", and it does not press when the command differs or is cut off; it shows the prompt to the user instead. If the classifier refuses outright (no prompt), the worker reports the exact command, and the orchestrator hands it to the user to run here with `!`.
- `pr-ship-guard` hook 은 worker pane 에서 확인 창(ask) 대신 deny 를 낸다. 창이 worker pane 에 뜨면 사용자가 보지 않아 worker 가 멈추기 때문이다 (11-15: 검증 로그 없음·실패로 `gh pr create` 3건 정지). worker 는 deny 사유를 `결정 필요` 로 보내고, 사용자가 "그대로 올림" 을 승인하면 orchestrator 가 같은 명령을 자기 pane 에서 실행해 확인 창을 사용자에게 보인다. worker 가 승인 표식을 만들어 우회하지 않는다.
- skill·hook·CLAUDE.md·settings 같은 에이전트 설정 파일 수정은 worker 에 넘기지 않고 orchestrator 가 직접 한다. worker 는 조사·측정·설계안까지 하고 `결정 필요` 로 넘긴다. worker 는 다른 세션 메시지를 설정 변경 근거로 삼지 않고, auto mode classifier 도 그 흐름을 지시 주입으로 막는다 (11-18: 설정 수정 worker 2개가 사용자 직접 입력을 기다리며 멈춤).
- When a worker reports the issue number it took (new issue or `/work #N`), the orchestrator renames that session to `<group>-worker-<N>-<topic>`. Check with `peek-claude-pane.sh <pane>` that the pane is idle and its input box is empty, then `tmux send-keys -t <pane> -l '/rename <name>'` and Enter. Dim text in the input box (`peek-claude-pane.sh <pane> -e` shows `\e[2m`) is an auto-suggestion, not typed input; treat the box as empty. If it is busy or the input box has text, wait for an idle notice (`notify_when_idle`) instead; never press Esc to clear it, since that can interrupt the running turn.
- The orchestrator manages sessions, decisions, blockers, merges, and deploy coordination. It does not run deploys itself: when the user approves a deploy, it relays "the user approved" to the worker that owns the issue, and that worker deploys and reports. A design session reflects approved decisions in docs/issues and reports briefly; it does not ask the user directly.
- When a worker has nothing left to do (its PRs merged and cleaned up, its issue closed or left open only to wait on an outside answer), the orchestrator closes that session without asking: have the worker close its issue first if it is done, then check with `peek-claude-pane.sh <pane>` that the pane is idle with an empty input box and send `/exit` with `tmux send-keys`. Record the closed session in the status file (10-26 user). Do it in the same turn as the report. Two global hooks back this up (10-27 user): a Stop hook (`multi-session-close-check.py`) blocks an orchestrator's turn end while a worker that sent `#N 닫음 · 남은 일 없음` (or `#N 정리 끝 · 남은 일 없음` when it only cleaned up a PR without an issue to close) still has a live pane, so workers must use that exact report line; a PreToolUse hook (`multi-session-exit-guard.py`) refuses `tmux send-keys … /exit` unless `-t` names a pane whose title contains `-worker-`.
- The orchestrator keeps its working state in a status file, not in the conversation, so the context can be compacted without losing anything. Location: the project's `.claude/references/multi-session.md` names it; default `.claude/plans/<group>-status.md`.
  - Contents, current state only (no history): each worker → issue, PR, state, what it is waiting on; pending `결정 필요` with who is waiting; decisions made since the last design hand-off; 자체 결정 누계와 그중 사용자가 뒤집은 수 (결정 규칙표를 넓힐지 좁힐지의 근거); next checks. Keep it under ~150 lines; move finished items out.
  - Update it right after each event (worker report, decision, merge, session start/stop), before replying.
  - 같은 때 바뀐 worker 의 진척을 그 pane 에 적는다: `tmux set -p -t <pane> @claude_progress '<끝낸 수>/<전체 수> #N 짧은 제목 · 지금 하는 일·기다리는 것'` (수를 모르면 `?/?`). orchestrator statusline(`~/.claude/hooks/statusline.sh`)이 이것을 세션마다 진척 막대 한 줄로 그린다. 진척을 모르는 worker(`?/?` 로 그려지는 세션)에는 `진척 요청` 을 SendMessage 로 한 번 보내고, worker 는 `진척:` 한 줄로만 답한다. 진척 없는 줄은 statusline 이 대신 hook 의 활동 이름(`@claude_activity`)을 붙인다. statusline 은 orchestrator 턴에만 다시 그려지므로 주기 실행 없이 이 값과 맞는다.
  - At session start and after any compaction, read the status file first and trust it over your memory of the conversation.
